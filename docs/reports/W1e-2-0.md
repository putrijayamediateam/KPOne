## Scope and behaviour

A plan freezes site-level inputs separately from its currently approved website release. It binds the release number and manifest hash to canonical JSON, a SHA-256 plan hash and a separately allocated `WEBPLAN/{local year}/{6 digits}` number. No missing value is filled from drafts, internal slugs, business settings, staff records or the old website.

The private release workspace gains an output-plan list and an approved-release prepare link. The prepare form has typed aliases beside frozen English item names, fixed available-page checkboxes, optional EN/BM footer lines, an optional existing-media logo and readiness notices. Detail shows escaped structured data, hashes, state, creator/approver names and action history. This is a **structured plan**, not a website preview or renderer. Branch switching clears loaded content, fields, errors and confirmation.

Preparation requires every included branch, category and service alias in one response; invalid, missing, duplicate and unknown item keys are refused together without retaining a plan or consuming a number. Aliases are 3–60 lowercase ASCII letters/digits with single internal hyphens, unique within their kind. Service-detail addresses retain the `?slug=` style. Optional footers are at most 200 characters per language. Public origin is lowercased, at most 100 characters, HTTPS DNS host only, without path (including trailing slash), query, fragment, userinfo or port. Markup, control, bidi and zero-width characters are refused by the existing text cleaner. Unknown plan fields and unavailable pages are refused.

Prepared plans can be approved or refused; approved plans can be withdrawn. Approval needs the exact typed plan number, current version and hash, and a still-approved bound release. Refusal/withdrawal require a plain-text reason of at most 300 characters. A release withdrawal never rewrites plan evidence; the plan becomes unusable for future builds. A matching retry returns its original result after fresh authority checks; a conflicting payload or actor is refused.

## Tables, migration and shared extraction

One additive migration: `2026_10_27_000100_create_website_output_plans.php`.

| Table | Purpose and PostgreSQL protection |
|---|---|
| `website_output_plans` | Immutable canonical content, hash, source release binding, number and creator/time. Guarded insert locks and checks the exact approved source release, organisation and binding/hash. |
| `website_output_plan_controls` | Independent state and optimistic `lock_version`; only prepared → approved/refused and approved → withdrawn with exactly one version increment. Delete/truncate refused. |
| `website_output_plan_actions` | Append-only actor ids, action, hash, reason and UTC time. |
| `website_output_plan_commands` | Append-only organisation-scoped UUID retry keys, actor, operation and HMAC payload fingerprint. |
| `website_output_plan_counters` | Locked organisation/year counter; increments exactly once, never decrements; delete/truncate refused. |
| `website_output_plan_assets` | At most one immutable logo per plan, source asset provenance, hash/MIME/size/dimensions/EN/BM alt text and encrypted retained bytes. |

Immutable tables refuse update, delete and truncate. Deferred completeness checks require the initial control/action/command and exact matching logo metadata before commit. Logo insertion closes when the preparation action is recorded. `down()` retains all evidence and counters. Existing databases need `php artisan migrate`. No existing release table, guard or migration changes.

`WebsiteMediaCapture` extracts the existing release-media checks verbatim; `WebsiteReleaseSelection` calls it without changing release behaviour or its error. Plan logos must be sanitised, active and same-organisation, have a rights reference and both alt texts, and have a consent reference if they show an identifiable person. Retained bytes must decode and match the recorded hash, MIME, dimensions and length. The plan encrypts its own copy. Later source retirement, metadata edits or file removal cannot rewrite that copy. No new media-serving route is added.

Other files: `WebsiteOutputPlanFields`, `WebsiteOutputProfile`, `WebsiteOutputPlanService`, `WebsiteOutputPlanController`, private routes, the `OutputPlans.vue` page and TypeScript contracts; a small Releases-page integration and middleware exclusion from unrelated pending-intake shared props. No dependency, permission, catalogue or role-grant change.

## Permissions and safety

| Existing permission | Holders | Plan operations |
|---|---|---|
| `website.releases.prepare.organisation` | Director, Marketing, Administrator | View and prepare |
| `website.releases.approve.organisation` | Director only | Approve, refuse and withdraw (also requires prepare authority) |

All other catalogue roles, including HR Manager, receive no output-plan access. Director-only provisioning and all staff-authority rules remain unchanged.

Every mutation uses fresh organisation/permission/effective-branch authority, a transaction, consistent authority/organisation → counter → release/control → plan/control → media locks, independent versions, UUID retries and audit rollback. Audit records only plan/release ids, number, action, hash prefix and alias/asset counts, never plan text, origin, aliases, footer, names or reasons. Reads are private/no-store/noindex and do not claim that anything was published. Display names come from at most one organisation-scoped `select name, id from users ... id in (...)` lookup per page, restricted to displayed creator/approver/history actor ids; names never enter evidence. Mutation logic performs no display-name lookup.

The query-boundary test permits only existing acting-user authority reads plus the page-only names lookup. It forbids draft revisions, business settings and operational/clinical/financial sources. Full ID-ordered snapshots compare every unrelated table after prepare, page read, approve, refuse and withdraw; a populated clinical/billing fixture is present. Audit-failure tests compare **all** rows, including plan records and audit, to prove rollback. HTTP requests and queued jobs are forbidden/asserted absent. No public route, file serving, outbound application call, job, old-website code or data is introduced.

## Limits, readiness and open questions

1. **Owner review:** approve the fixed EN/BM navigation labels and `kp-soft-v1` palette before a renderer uses them. This candidate does not claim production or wording approval.
2. **About is absent**, as instructed. A logo may be omitted and is a readiness note, not a plan-preparation blocker. Neither causes a live fallback.
3. Origin validation conservatively requires a dotted DNS hostname and refuses IP/localhost origins. A synthetic `.test` hostname works for review. Confirm the real origin later; no DNS lookup or outbound validation occurs.
4. Numbering uses the release pattern: the active branches must share one organisation-local timezone. Mixed active timezones are refused; UTC timestamps remain stored.
5. Refusal/withdrawal remain available for closing a historical plan after its source release is withdrawn; approval and future-build usability are refused. Exact successful retries return their original result without restoring usability.
6. Plan lists are unpaginated, matching the small release workspace. Large-scale history/load behaviour has not been benchmarked. Each chosen logo is a separate encrypted database copy; no purge is introduced.
7. Future renderer/artifact work must use only the frozen release and plan, verify hashes, and recheck both approval states. Actual routing, SEO parity/redirects, website HTML, artifacts/storage rules, artifact approval, deployment/Cloudflare, public APIs, forms/intake, analytics, third-party embeds, About/legal content and imports remain absent and unauthorised by this job.
