## Today
- Q-11 fills vitals typed in the clinical note and flags a value outside `USUAL` ranges (my placeholder, "PENDING DOCTOR CONFIRMATION") as "Check: BP 180/45 (unusual value; is it a typo in the note?)".
- The approved source is the TRI-1a guideline: `TriageGuidelineService::inForce($organisationId)` returns the approved version with `thresholds` (reading, age_band adult|child, direction very_low|very_high, limit_value, zone yellow|red), signed by Dr Fatin Adilah. `TriageService::limits()` (static) shapes them. `TriageService::ageBand()` gives adult / child / unknown from the date of birth or the adult confirmation.
- The doctor's consultation payload carries no triage data today. The guideline reaches the CA's triage form only (`visits.triage.record.branch`); only the Director and HR Manager manage it (`triage.guideline.manage.organisation`).
- `resources/js/lib/triage-zone.ts` already has the pure comparison used by the triage form: `suggest(readings, redFlags, yellowSigns, ageBand, limits)` returns `crossed` (per reading: direction and zone), in whole hundredths, mirroring PHP and SQL.

## Proposed
1. **Payload (read only).** `ClinicalEncounterDirectoryService::detail()` adds `vitalLimits`: `null` when no guideline is in force or the doctor lacks the permission, otherwise `{ versionNumber, ageBand, limits: [{reading, age_band, direction, limit_value, zone}] }`. Limits and the age band only: no sign labels, no red flags, no names, no patient data (the date of birth is already on the doctor's page; the age band adds nothing new). Built from `inForce()` (a plain read with no gate, lock or audit when `lock = false`; the caller gates) and `TriageService::limits()`. `inForce()` also loads the signs, which the payload never sends (filtered in PHP; about 3 extra queries on `detail()`, which has no poll). A guideline with no thresholds gives `limits: []`, so no flag. The age band comes from `TriageService::ageBand()` with the visit and the branch time zone `detail()` already has; the doctor already sees the date of birth, so this adds nothing. The payload key is top-level on `detail()` (not inside `vitals` or `encounter`), and a page keeps the limits it loaded (a newer approval changes nothing until reload; the version number is on the line).
2. **Rule in the browser.** The helper compares in whole hundredths with `triage-zone.ts`'s `suggest(readings, [], [], ageBand, limits)`: inclusive (`very_high` flags value >= limit, `very_low` value <= limit); `crossed[reading]` holds the highest zone crossed (a reading past red reports red only); a reading with no limit is never flagged; weight and height flag only if the guideline holds a limit for them (no extra code). For BP, one chip carries two fields: any crossed field flags the chip, and its tone is the highest zone of its fields. **Age band unknown** (no date of birth and no adult confirmation): `suggest()` checks both adult and child limits, as the triage form does, so a child limit tighter than the adult one can flag an adult-normal reading; the note recommends matching triage (open question 4). `isUnusual()` and the `USUAL` table are replaced by a helper that calls `triage-zone.ts`'s comparison with `vitalLimits`: a filled reading "crosses" a limit when `suggest()` reports it. Same filled value, same Fill / Undo / "Not filled" behaviour; only the flag changes. **No guideline in force means no Check flag** (owner rule).
3. **Wording and tones.** A reading that crosses a **yellow** limit: "Check: BP 180/45 (outside the clinic's usual range; is it a typo in the note?)". One that crosses a **red** limit: the same line with "(outside the clinic's red limit)". Warning tokens for both, the red one with a stronger weight (not the destructive colour, so the note never reads as a diagnosis). Which of the two the owner wants shown is an open question below. The line states the clinic's guideline version ("TRI guideline v3") in small muted text so the doctor knows the source.
4. **Permission (needs the owner's approval before use).** The narrowest option: `triage.guideline.view_limits.organisation`, **read-only**, **granted to `resident_doctor` only**, added by an additive migration and mirrored in `PermissionCatalogue`/`TriagePermissions`. It exposes reference limits only (no signs, no patient readings), is not people or access authority, and implies no triage write. The consultation service checks it fresh; without it `vitalLimits` is `null` and no Check flag shows. Alternative for the owner (no new permission): gate the payload by the doctor's existing `encounters.view.own`, since it only rides the doctor's own consultation payload.
5. No new route, page or poll. Frontend change is small (the line's wording and a helper swap); Daniel looks at the line if its wording or tone changes.
