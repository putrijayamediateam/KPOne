`wrapper-readable.txt` source lines 244–254, 286, 291, 545 establish that PatientDirectory opens **Registration:patients**, QrCheckins opens **Registration:qr**, RegToday opens **Registration:board**, RegFollowUp opens **Registration:followup**. PatientMerge redirects to **Admin:merge**. Therefore a matching standalone legacy asset is not sufficient runtime parity. `WfRegisterVisit` is in `NOTES` and hidden; it is explanatory material, not an additional deliverable page. Wrapper permission/action filters are not permission grants. Its light-color override is not a reason to regress supported dark mode. Example buttons, hard-coded patients and simulation-only field cycling are demo controls, not production requirements.

## Proposed implementation order (plan only)

1. Registration workspace navigation and shared patient-directory/QR surfaces, using existing routes/data. Capture exact tab URL/back-navigation and responsive acceptance states first. Keep status filters subordinate to Today; preserve approved emergency lane/readiness behavior.
2. Register visit and patient create/edit reusable dialog surfaces, four-stage/check summary and dirty-state handling. Retain accessible full-page fallback; preserve all approved atomic registration/contact commands.
3. Patient overview composition. First inventory existing permission-scoped visit/billing/clinical APIs with their owners; supply only authorized cards. This is more than CSS and should not be bundled as a pure restyle.
4. Registration follow-up and all-branch dashboard as distinct data/workflow slices with explicit service/authority review before implementation. Admin merge and Billing follow-ons remain coordinated ownership interfaces.

Before each slice, prepare exact existing assertion changes for the owner's required approval batch; add new behavioral tests for navigation, privacy and modal lifecycle. No assertion updates are authorized by this audit. Fresh light/dark 390/1440 browser comparisons, keyboard/close/error/retry states and actual backend transitions remain required. Do not conflate source presence or earlier screenshot review with end-to-end demo completion.
