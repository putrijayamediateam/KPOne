# Q1-B2-D3 release notes

Branch `fix/q1-b2-d3-registration-qr-hold`, remediated in Q1-B2-D3-R1. Not a release or production
approval — see `docs/BASELINE.md`. This document is the operational checklist for deploying this
branch to any environment (staging, UAT, or eventually production once separately authorised).

## Migrations to run

Run migrations in the normal way; no manual step is required beyond `php artisan migrate --force`:

```
2026_09_21_000100_create_consultation_holds
2026_09_22_000100_sync_permission_catalogue_additively
```

`create_consultation_holds` adds the `consultation_holds` table only. It is purely additive and its
`down()` drops that one table.

`sync_permission_catalogue_additively` is the R1-02 permission rollout (below). It is purely
additive and its `down()` is intentionally a no-op — it never removes a permission or grant, since
some of what it adds may already exist from `KPOneReferenceSeeder` or a prior run of the same
migration.

## Permissions now apply via migration (R1-02)

Before this release, a new `PermissionCatalogue` entry existed in code but did not exist in an
already-migrated database until someone remembered to run
`php artisan db:seed --class=KPOneReferenceSeeder --force`. Nothing in CI or the standard deploy
path ran that seeder automatically, so `consultations.hold.own` (and, in principle, any earlier
phase's new permission) could silently not exist after a routine deploy.

`2026_09_22_000100_sync_permission_catalogue_additively` closes that gap: after `php artisan
migrate` alone, every permission in `PermissionCatalogue::all()` exists, and every role in
`PermissionCatalogue::roles()` that already exists in the database holds every permission the
catalogue assigns it. It only ever adds — a permission grant made outside the catalogue is never
touched, and a catalogue role missing from the database is never auto-created (a structural warning
is logged with the role's name instead; creating a new role stays `KPOneReferenceSeeder`'s job, run
once for that new role).

**This is now the standard pattern going forward:** a phase that adds a permission to
`PermissionCatalogue` ships it as an additive migration in this same shape (see
`tests/Feature/Access/PermissionCatalogueMigrationTest.php` for the scenarios it must keep passing:
migrate-only, seed-then-migrate, migrate-then-seed, re-running the migration, an out-of-catalogue
grant, and a missing catalogue role). `KPOneReferenceSeeder` is unchanged and remains how a brand
new installation is bootstrapped from nothing.

## Required environment variable

`PUBLIC_PATIENT_INTAKE_TRUSTED_PROXIES` must be set to the real upstream proxy IP(s) in any
environment reachable through a load balancer or reverse proxy (staging, UAT, production). If it is
left empty:

- Rate limiting on the public check-in/intake routes keys off the proxy's own IP address instead of
  the real visitor's, so many visitors share one limiter bucket and can throttle each other.
- `PublicCheckInController`'s protected cookies fall back to the request's own reported scheme
  (`$request->isSecure()`) rather than the deployment's actual TLS posture, which — behind a
  TLS-terminating proxy — under-reports HTTPS and can mark cookies non-Secure when the deployment is
  in fact served over HTTPS. Set `SESSION_SECURE_COOKIE=true` explicitly in that case (R1-09); it
  now always takes precedence over the per-request scheme when set.

## Scheduler requirement

`public-intakes:cleanup` (expire stale intakes, purge retained payloads past retention, and prune
abandoned `public_intake_sessions`) is now registered on the schedule
(`withoutOverlapping()->onOneServer()`, daily) in `routes/console.php`. The application's own
scheduler must actually run for this to fire: ensure the environment's cron (or equivalent) invokes
`php artisan schedule:run` every minute, exactly as any other Laravel scheduled command requires.
This was previously **not scheduled at all** — the only way it ran was a manual
`php artisan public-intakes:cleanup` invocation.

## Existing QR check-in links must be rotated

D3 changed the public check-in URL format to `/check-in#token` (the bearer travels only in the URL
fragment, exchanged for httpOnly cookies — see `docs/BASELINE.md` §5). A link issued before this
change has no recoverable raw token under the new format and cannot be redisplayed.

No data backfill is written or needed. The QR management page
(`resources/js/pages/PublicCheckInLinks/Index.vue`, driven by
`PublicCheckInLinkController::index()`'s existing `requiresRotation` flag) already shows any such
link with an explicit notice ("QR lama ini tidak boleh dipaparkan semula...") and a **Rotate**
action in place of the QR/copy/download/print controls. Rotating issues a fresh link in the current
format. Before UAT or go-live, an administrator should open QR management for every branch and
rotate (and reprint) any link still showing that notice.
